# PR差分からRailsのrequest spec・system specを選ぶ

提案段階。SukashiはRailsアプリのCIで、PRの変更に関係するRSpecファイルと選んだ理由を出す。初版はファイル単位とし、同じファイルのexample、フック、共有contextを一緒に実行する。他の種類のspecは既存のCIが担当する。

**推奨は、Prismによる選択を先に作り、全件実行と照合したあとで、必要な箇所に実行履歴を足す方式。** 初日から過去の計測データなしで使え、履歴の追加によって選択結果がどう変わるかを同じPRで比較できる。

## Crystalballから何を取り入れるか

GitLabは、RubyのCoverageとCrystalballで「そのソースファイルを実行したspec」の対応表を作り、差分からテストを逆引きする方式を採用した。たとえばモデルに、対応するモデルspec以外のspecも結び付く。Sukashiでもこの逆引きを使う。新規コードや前回通らなかった分岐についてはPRのソースから別途依存を拾う。[GitLabの方式選定とマップ例](https://gitlab.com/gitlab-org/gitlab/-/issues/263421)・[Crystalball](https://github.com/pluff/crystalball)

## 選択アルゴリズム

入力はPRの比較先commit、PR head、対象specの探索パターン（既定は `spec/{requests,system}/**/*_spec.rb`）。利用側で独自配置を含め、全件ジョブと同じ対象集合を列挙する。「全件」は以下、この集合内のheadに存在する全ファイルを指す。

1. **差分を確定する。** 比較先とheadのmerge-baseをB、実行対象のheadをHとする。`git diff --name-status -z -M B H` で、追加はHのパス、削除はBのパス、変更・移動は両側を記録する。CIもHをcheckoutする。履歴不足でBが得られなければfetchを試し、確定できなければ全件へ戻す。
2. **BとHに依存グラフを作る。** ノードの単位はリポジトリ相対パス。辺は「利用ファイル → 定義ファイル」とし、根拠（定数名、route helperなど）と位置を付ける。RubyをPrismでparseし、定数定義とDSL宣言を先に索引化してから、visitorで参照を解決する。再オープンや同名候補は全候補につなぐ。クラス名の単純な末尾一致で一つに決めない。初版は両treeを全走査し、最適化する場合も名前解決は各treeの索引でやり直す。[PrismのRuby API](https://ruby.github.io/prism/rb/docs/ruby_api_md.html)
3. **変更ごとに逆引きする。** 各側の変更パスから逆辺を幅優先でたどり、到達した対象specを集める。訪問済み集合で循環を止める。B側で見つけたspecは移動情報でHの名前に直し、Hで存在を確認する。変更・追加された対象spec自身も必ず加える。実行履歴を使う案では、次の拡大規則まで適用した静的な選択結果に、Bでの観測から得た現存specを加える。各specには少なくとも一つの根拠経路を残す。グラフ構築後の探索は、始点をまとめれば各treeで最大 O(ノード数 + 辺数)。
4. **取りこぼしを扱ってから実行する。** 下表の拡大規則を変更パスごとに適用し、全変更の結果を和集合にする。一つの変更がspecに当たっても、別の未分類の変更を打ち消さない。Hにあるファイルを重複排除してパス順に並べる。

### RailsとRSpecの境界

| 変更・参照 | 初版で選ぶ範囲と理由 |
| --- | --- |
| モデル、サービス、concern | 字句スコープを考慮した定数参照、継承、include、リテラルの `require_relative` を結ぶ。通常のインスタンスメソッドは所有ファイル単位で扱う。 |
| HTTPリクエストと画面遷移 | 単純な `resources` とリテラルのHTTP動詞・パス・遷移先から、route helperまたは動詞＋パスとcontrollerファイルを対応付ける。`get orders_path`（request）、`visit orders_path`（system）の両方を結ぶ。初版で対応しないengine、動的URL、ボタン操作などは未解決の利用として記録する。 |
| FactoryBot、shared examples/context | リテラル名で利用元と宣言元を結ぶ。factoryのクラスと静的に分かる親factoryもたどる。衝突は全候補、動的な名前は未解決として扱う。 |
| view、partial、layout | request specもHTMLを検証できる。初版はテンプレート変更で両種を全件。PrismにERB全体は渡さない。ブラウザ用JS/CSSはsystem全件に広げる。assetの内容や配信をrequestでも検査するアプリは両種に広げる。 |
| `config/routes.rb`、initializer、DBスキーマ・migration、Gemfile.lock、共通spec helper、選択器の設定 | アプリ全体の挙動またはspecの探索結果が変わり得るので両種を全件。 |
| ドキュメントだけ | 解析・実行に使うファイルの規則を優先し、それ以外で実行時に読まれないと利用側が明示したパスだけ省略可。変更がすべてこの範囲なら0件を正常とする。 |
| 分類できない変更、parse失敗、依存先を引けない実行コード変更 | 両種を全件。新規ファイルにも適用する。削除されたspecは実行せず、他ファイルから参照されていればBの逆引き結果を使う。移動元specと移動先を対応付けられない場合も、追加されたspecは自身の変更として選ぶ。 |

未解決参照は**利用元にも**記録する。たとえばsystem specが `visit url_for(record)` を使う場合、controllerを変更したPRで別のrequest specが静的にヒットしても、このsystem specを含める。初版では、未解決参照を持つファイルを利用するspecをアプリコード変更時に常時加える。共通フックや自動ロードなどでその利用元を限定できなければ全件に広げる。暗黙のcallbackや別プロセスへの通信を網羅的に認識することは難しく、実アプリでの照合が必要になる。

### 選択結果の例

`OrderTotal` を `OrdersController` が利用し、注文一覧のrequest specとsystem specがともに `orders_path` を呼ぶとする。サービスだけを変更したPRの説明は次のようになる（矢印は変更から利用元への逆引き）。

```text
app/services/order_total.rb
  └─ OrderTotal → app/controllers/orders_controller.rb
       ├─ GET orders_path   → spec/requests/orders_spec.rb
       └─ visit orders_path → spec/system/order_history_spec.rb
```

同じPRで `app/views/orders/_total.html.erb` も変更すれば両種を全件実行し、理由にpartialのパスを出す。サービスを移動し、旧定数への依存がheadから消えた場合でも、B側でつながっていた現存specは選択に残る。

## 実行履歴を加える場合

Bで成功した全件実行から `source_path → [spec_path, ...]` を作る。最初の計測器はspecファイルごとに独立したRubyプロセスでCoverageを起動し、アプリのロード前から終了までに実行されたリポジトリ内の行をファイルに集約する。起動時の共通コードも含める。計測コストが大きい場合は、選択時の短縮分と計測コストを別々に評価する。

- 各workerは自分のspec集合・結果・辺を出力する。全件の列挙結果と照合し、欠落、途中失敗、対象外フィルタがある実行は公開しない。
- 別プロセスのRailsサーバーを使うsystem specではRSpec側のCoverageだけではcontrollerを観測できない。専用サーバーをspec単位で起動して合算できる場合に限ってその対応を使う。共有サーバーで帰属が不明なら該当system specを常時加える。JS/CSSとテンプレートには上表を適用する。
- manifestにはリポジトリ、BのSHA、形式版、Ruby・計測器・設定・依存の識別子、対象spec一覧と完了状態を保存する。信頼する比較元CIの成果物だけを読む。Bと一致する完全な成果物がなければ静的案に戻し、その理由を表示する。
- 観測は候補の追加だけに使う。過去の実行で触れなかったことを除外理由にはしない。未解決時の拡大を実測で緩める判断は、初版の後で別途行う。

## CIとの契約

提案するCLIは `bundle exec sukashi plan --base <比較先SHA> --head <PRのSHA>` でJSONを出し、`bundle exec sukashi run --plan <ファイル>` で実行する。planにはB・H、対象集合、モード（subset / full / skip）、選択パス、根拠または拡大理由を含める。runはHと対象集合の一致を確認し、列挙したパスを個別の引数としてRSpecへ渡し、RSpecの終了ステータスを返す。skipは、差分なし、明示的に省略できるパスのみ、または単独のspec削除で現存する利用元がないと確認できた場合に限り、RSpecを起動しない。それ以外で選択結果が空なら全件とする。対象specがあるはずなのに探索できない場合や、planが壊れた場合は既存の全件ジョブへ戻す。全件も実行できなければCIを失敗させる。

## 比較と相談事項

| 方式 | PRで使う入力 | 導入と運用の違い | 適した段階 |
| --- | --- | --- | --- |
| 静的案（PrismとRails規則） | B/Hのソース | 初回から動く。間接参照や画面変更が多いと全件に戻る頻度が高い | 小さく導入し、拡大理由を知りたい |
| 併用案（Prism＋実行履歴） | 静的案の入力と、merge-baseの全件計測マップ | 常に静的案の上位集合で、静的規則が見落とした実行経路を追加できる。計測時間・成果物の管理が増える | 代表アプリで静的案の選択漏れを検証したい |

**相談したいのは、最初の実装に全件計測と成果物管理まで含めるか。** 推奨の順序は 静的案 → 実アプリで照合 → 実行履歴を追加。初回からsystem specの実行経路を収集したい場合は、同じ静的選択器に計測器を組み合わせて併用案から始められる。履歴の追加だけで実行本数が減ることはない。

## 実装と採否の確認

1. **差分・Prism索引・planを作る。** 小さなRails fixtureに上の注文例と無関係なspecを置く。サービス変更で対象2本を含み無関係なspecを省くこと、rename/deleteで旧経路を拾うこと、追加spec・動的URL・混在差分・parse失敗・明示した文書だけのPRでそれぞれ期待した集合になることを検証する。
2. **CIで選択結果と全件を並走させる。** 同じHの全件で再現する失敗ファイルが選択集合の外にあれば選択漏れとして記録する。実際に壊れる変更をfixtureにも入れ、選択実行が失敗を検出することを確認する。緑のPRだけでは漏れを測れない。
3. **代表アプリで判断する。** PR別に、両種それぞれの選択数／総数、全件化の理由、plan生成を含む所要時間、再現した選択漏れを残す。漏れの原因を説明・修正でき、全件より待ち時間が短くなった範囲から選択実行を有効にする。導入後も定期的な全件実行とPRの抜き取り照合を残し、漏れを再現した分類は全件へ戻す。
