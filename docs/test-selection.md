# PRの変更分岐からRSpec・Minitestのテストを選ぶ

Sukashiの対象は、プロジェクトがRSpecまたはMinitestで実行するすべてのテスト。Railsのrequest specとsystem specも含む。Rubyライブラリの単体テスト、Railsのモデル・ジョブ・メーラー、HTTP経由の統合テスト、ブラウザを使うシステムテストまで、種類やディレクトリで対象を限定しない。

初版ではPrismで変更された分岐と、そこに到達し得るテストを対応付け、PRごとに全件実行と照合する。個別に解析できるテストから絞り込み、未対応のDSLや動的に生成されたテストもファイル単位またはスイート全件で実行する。実行履歴を収集するかは照合結果を見て決める。

## Crystalballから取り入れる仕組み

GitLabの導入MRでは、Crystalballが記録した「各RSpec exampleが触れたソースファイル」を「ソースファイル → specファイル一覧」に集約した。同じサービスの通常注文とギフト注文が別分岐を通っても、この表では同じキーになる。Sukashiも差分から逆引きするが、条件式・then本体・else本体を区別し、同じファイル内のテストを個別に選べるようにする。[GitLabの導入MR](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/44968)

## ギフト手数料だけを変更したPR

```ruby
def self.fee(gift)
  if gift
    500   # この金額だけを700に変更
  else
    100
  end
end
```

以下はRSpecとMinitestが混在する例。ギフト用と通常用のactionは、それぞれ `OrderFee.fee(true)` と `OrderFee.fee(false)` を呼ぶ。二つのrequest exampleは同じファイルにあり、各actionへの経路は一意とする。

| テスト | 解析できた経路 | ギフト金額の変更 | 条件式の変更 |
| --- | --- | --- | --- |
| RSpec・ギフト注文のrequest | ギフトURL → action → true → then | 実行 | 実行 |
| RSpec・通常注文のrequest | 通常URL → action → false → else | 省略 | 実行 |
| RSpec・画面から注文するsystem | ボタン操作後の遷移先が不明 | 実行 | 実行 |
| Minitest・通常料金の単体テスト | テストから直接false → else | 省略 | 実行 |
| Minitest・ギフト料金の単体テスト | テストから直接true → then | 実行 | 実行 |

金額だけなら5件中3件、条件式を変えれば5件が設計上の期待値。Prismから得られるのは分岐の構造とソース範囲であり、true/falseは呼び出し経路の引数を解析して求める。[Prism::IfNode](https://ruby.github.io/prism/rb/Prism/IfNode.html)

## テストの列挙と実行

全件の基準は、利用プロジェクトの各テストジョブがPR headで実行するテストの和集合とする。各ランナーの起動コマンド、環境、設定、独自の探索パターンを引き継ぐ。たとえばRailsのMinitestでは `bin/rails test:all`、または通常テストとsystemテストの両ジョブを登録する。RSpecの独自typeや独自ディレクトリも、そのジョブで実行されれば対象に入る。[Rails Testing Guide](https://guides.rubyonrails.org/testing.html#running-tests-in-continuous-integration-ci)

ランナーが全件設定で列挙した各テストを「ジョブ・ランナー・その版でのID・定義位置」で表す。同じ名前を持つテスト、異なる設定で同じテストを動かすジョブを区別する。Prismの共通部分はこの一覧を使い、ランナー別の処理が個々の定義との照合と実行を受け持つ。

| ランナー | テストの識別と実行 |
| --- | --- |
| RSpec | 同じ設定で列挙したexample IDと定義位置を使う。一意に対応する場合は `spec/requests/orders_spec.rb[1:2]` のようなIDを個別の引数で渡す。shared examplesや動的なexampleで帰属が曖昧なら、それらを含むファイル全体に広げる。 |
| Minitest | ロード後の実行対象クラスと登録されたテストメソッド名を組にする。`def test_*`、Railsの `test "..."`、Minitest::Specの `it` も実際の登録名に照合する。個別に起動できるランナーでは完全修飾名に完全一致するフィルタを渡す（例 `--name '/\AFeeTest#test_gift\z/'`）。継承や動的定義で定義位置から実行クラスを限定できなければ全候補を残し、ファイルで包含できなければジョブ全件に広げる。[Minitestの実行オプション](https://github.com/minitest/minitest#running-your-tests) |

RSpecのみ、Minitestのみ、併用のいずれでも、設定した全ジョブが判定に参加する。列挙や個別指定に対応していないジョブは既存の全件コマンドで実行する。初版から「解析できないテストも対象に含まれる」ことを、この全件コマンドとの照合で確認する。

## 選択アルゴリズム

1. **差分を確定する。** 比較先とPR headのmerge-baseをB、実行対象のheadをHとする。`git diff --name-status -z -M B H` を使い、追加はH側、削除はB側、変更・移動は両側でパスを記録する。Bを取得できなければ全件を実行する。
2. **BとHに依存グラフを作る。** Prismで各版のRubyをparseし、定数・メソッド・DSL宣言を索引化してから参照を解決する。まず「利用ファイル → 定義ファイル」の辺を作り、定数名、route helper、定義位置などの根拠を残す。字句スコープ、継承、include、リテラルの `require_relative` を考慮し、クラスの再オープンや同名候補は全候補につなぐ。[PrismのRuby API](https://ruby.github.io/prism/rb/docs/ruby_api_md.html)
3. **変更ごとに候補を逆引きする。** 各側の変更パスから逆辺を幅優先でたどり、到達したテストを集める。訪問済み集合で循環を止める。B側の候補は移動情報を使ってH側へ対応付ける。変更・追加されたテストファイルは全体を必ず加える。削除されたテストの利用元がHに残っていればその利用元を選ぶ。
4. **分岐で絞る。** 下記の条件が成立する変更について、粗い候補をテスト単位に絞る。未解決の経路、共通設定などの拡大規則を適用してから、全変更の結果をジョブごとに和集合にする。同じファイルに全体指定と個別指定があれば全体指定を優先する。

### 分岐とテストの対応を残す

- **変更箇所の識別。** ファイル、クラス／モジュール、メソッド、分岐までのAST上の経路、then / elseをキーにする。行・byte範囲は版ごとに保存する。BとHで条件式、外側の構文、束縛、兄弟の順序を比較し、通常の `if 引数 ... else ... end` の片側でリテラルや明示的な呼び出しの引数だけが変わった場合から絞る。条件式の変更は両側を選ぶ。分岐の挿入・削除・並べ替えで対応が曖昧ならメソッド候補へ、所有者まで曖昧ならファイル候補へ広げる。
- **入力の伝播。** テスト本体や共有setupからの直接呼び出しをたどる。RailsのHTTPテストでは動詞・URLからcontrollerのactionを経由する。単純な仮引数にtrue/falseリテラルが渡り、再代入や介入がなく、呼び先が一意の場合だけ片側に絞る。DB値、feature flag、stub、動的送信が絡めば両側が候補。複数回呼ぶテストでは全経路を合算する。
- **保存と除外。** 各版で「分岐キーとthen / else → 到達し得るテストID集合」を根拠とともに保持する。ある変更で候補になったテストを外せるのは、B/Hの関連経路がすべて変更のない側に限定できた場合だけ。未解決のテストや共通フックは広い候補のまま残す。版をまたいでテストを一意に対応付けられないときは、Hの対応ファイル、必要ならジョブ全件を実行する。

### Railsや共有コードで範囲を広げる場合

| 変更・参照 | 選択規則 |
| --- | --- |
| HTTPと画面遷移 | 単純な `resources` やリテラルのルート定義から、HTTP動詞＋パスまたはroute helperとactionを結ぶ。request spec・integration testとsystem spec/testの両方で使う。engine、動的URL、ボタン操作など、未対応の経路を持つテストはアプリコード変更時に残す。 |
| factory、fixture、共有setup | リテラルの宣言名を利用元に結ぶ。RSpecのshared examplesやMinitestの継承したsetupも利用側に影響する。帰属を限定できない共通helperやfixtureは、利用し得るジョブ全件へ広げる。 |
| view、partial、layout、ブラウザ用asset | HTMLやassetを検査するテストには他の種類もある。初版は影響するジョブの全件とし、消費するジョブを限定できなければ全ジョブを選ぶ。 |
| routes、initializer、DBスキーマ・migration、依存ロック、選択器の設定 | 実行環境や経路が変わるため全ジョブを選ぶ。parse失敗、未分類の変更、新規を含む利用元不明の実行コードも全件に戻す。 |
| ドキュメント | 実行・解析に使わないと利用側が明示したパスだけ省略できる。他の変更の選択結果と合算する。 |

安全性の前提と対応する回帰テスト、精密化の判断に使うデータは [テストを省略できる前提と shadow 運用](selection-safety.md) にまとめる。設計上の候補と現在の実装範囲を区別し、全件照合を維持する。

## CIでの実行と検証

提案するCLIは `bundle exec sukashi plan --base <比較先SHA> --head <PRのSHA>` でJSONを出し、`bundle exec sukashi run --plan <ファイル>` で実行する。planにはB/H、ジョブ別の対象集合、モード（subset / full / skip）、選択IDまたはパス、分岐と選択理由を含める。runはHと設定を確認し、各ランナーが実行したIDをplanと照合する。予定したテストが欠けたりIDがずれたりした場合はそのジョブを全件で再実行する。テストの失敗はCIに伝え、全件実行も成立しない場合はCIを失敗させる。差分なし、明示的に省略可能な変更のみ、または利用元がない単独のテスト削除ならskipできる。それ以外で選択結果が空になれば全件に戻す。

1. 小さなRubyプロジェクトでRSpecのみ、Minitestのみの単体テストを通し、Railsアプリで両者が混在する上の5件を受け入れ例にする。独自ディレクトリのテスト、Minitestの同名メソッドを持つ別クラス、共有setup、動的テスト、rename/deleteも用意する。全件への拡大でテストが消えないことと、ギフト金額を壊したときに選択実行でも失敗を検出することを確かめる。
2. 代表プロジェクトの同じH・設定・seedで、分岐選択、ファイル単位の選択、既存の全件ジョブを比較する。当初のマージ判定は全件ジョブに置く。再現した失敗のIDが候補から漏れたら根拠経路を調査する。
3. ランナー・ジョブ別に選択件数／全件数、全件に戻した理由、列挙・解析・起動を含む経過時間を記録する。Railsではrequest、systemも個別に確認する。次に精密化する構文やテスト形式は、実際に広い候補へ戻った頻度と実行時間から決める。

## 将来、実行履歴を加えるなら

動的入力で両側を選ぶ事例が多ければ、Bの全件ジョブで `Coverage.start(branches: true)` を使う案を比較する。同じ版のソース範囲で実行カウンタをPrismの分岐に照合し、テストIDに帰属できた観測だけを別に持つ。RubyのCoverageはプロセス全体を計測するため、並列テストや別プロセスのRailsサーバーでは計測の分離が必要になる。観測で見つかった経路は候補に加える。観測されなかった経路を省略できる条件は別途検証する。[Ruby Coverage](https://docs.ruby-lang.org/en/master/Coverage.html)
